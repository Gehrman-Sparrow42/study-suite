# Operating rules for Study Suite V3

- Read PROGRESS.md before resuming setup; keep it current at coherent milestones.
- This is a reading resource. No quiz, flashcard, question-bank, self-test or practice-question interface. Worked examples may explain concepts and calculations.
- Use existing templates and scripts for future courses. Codex authors content from all supplied sources; no API-key summarizer.
- For every newly authored reader, populate course.study_brief with descriptive course/lecture context, supported lecturer-to-topic mapping, reported exam boundaries/exclusions/pending topics, source emphasis, uncertainty and clearly labelled opinions about study priorities. Keep the brief context-only: no instructions controlling the receiving AI’s teaching method, question generation, response format, sequencing or behavior. The receiving tutor chooses its own approach. Preserve evidence labels and refresh context on updates; never invent exam likelihoods. The builder embeds it outside the visible reading UI and in the portable snapshot.
- Read guidelines/CONTENT_GUIDELINES.md, VISUAL_GUIDELINES.md, CONTENT_SCHEMA.md and AUTHORING_CHECKLIST.md before authoring a course.
- Use concise, simple English and useful bullets. Formula keys explain domain variables, units, signs and assumptions, not elementary arithmetic. Verify that Review actually hides expanded explanations while retaining essential conditions.
- Present parallel facts, advantages, limits and alternatives as short semantic bullets, with selective bold domain terms or lead-ins. Keep causal explanations as prose where it reads better. Use the restricted formatting in CONTENT_SCHEMA.md; preserve formatting through editing, export and recovery. Do not bold whole paragraphs or turn every sentence into a bullet.
- Group an explanatory figure with its concept or comparison in a useful reading order; avoid large empty image frames, duplicate captions and tables mixing unrelated concerns. Keep figures compact and zoomable. After presentation changes, include actual rendered screenshots in the user-facing result and update the reusable guides with the lesson, not only the current course.
- Explain the subject directly. Omit routine "the instructor explains", "the lecture says" and similar narration from teaching prose. Attribute only when it clarifies a course-specific convention, genuine ambiguity, source disagreement or explicit exam instruction; put ordinary provenance in Source notes.
- Every worked example must state the problem, supplied data with units and required output before its solution. Put the task in its persistent summary and any essential givens there or immediately below it, before calculations. Keep these visible in Review. A title, answer or calculation sequence is not a problem statement; do not require readers to reconstruct the task from the solution or neighboring cards.
- Use English throughout. For a new course, normally author and deliver two separate editions together: focused_learning (recommended first reading) and balanced_high_yield (detailed reference). Core/cram is optional, not a third mandatory output. Current user instructions override this pair, then course config, then builder defaults.
- focused_learning keeps major concepts, causal explanations, important distinctions and essential applications while removing secondary catalogues, specialist detail and repeated examples. Learn must be a complete manageable reading path; Review is its refresher. Length follows course density, never a word count or fixed compression ratio. See guidelines/CONTENT_GUIDELINES.md.
- Inventory every input once and save edition-specific topic coverage maps with source locations and inclusion/omission decisions. Process in batches if needed, but produce one unified HTML per edition. Different depth labels require separately authored content; the builder does not summarize it.
- Give the two editions distinct stable course IDs, dated filenames and source JSON/config files. Preserve each edition's own saved edits separately. Never overwrite a detailed or personal edition to create the focused one.
- Save intermediate course work and a course-specific progress log in work/<course>/; do not commit private course inputs or generated course exports unless requested.
- Preserve true-black design, stable semantic colors, Learn/Review, browser text/formula edits, clean single-file export, embedded images and mobile navigation.
- Bionano L 1 to 10 is the PRIMARY experience reference for future suites, superseding the earlier prose-heavy V3 composition. Future outputs should be much closer to it: fluid topic-local card groups, semantic-colour titles rather than repeated category labels, strong section boundaries, full-width comparisons and synthesis callouts, restrained typography, short labelled explanations and visual process chains. Offer native expandable detail and keyboard-accessible section folding without fixed-height clipping. Choose structure by meaning, preserve logical reading order and editable/exportable content, and validate at the user's actual widescreen proportions as well as mobile with navigation open and closed. This is a broad authoring/design direction, not just a spacing patch.
- Do not rewrite or delete original references or source materials. Keep browser-edited exports separate from rebuilt files.
- Honor requests for in-place editorial corrections: update the existing requested HTML and its authored JSON, preserving saved edits, stable IDs, runtime and unrelated content. Do not create another HTML solely for that fix. This does not change the separate-edition preservation workflow for new weeks or different reading scopes.
- For new weeks, follow guidelines/WEEKLY_UPDATES.md. Scan the latest source registry, author only new material as a delta, preserve stable course/section/block IDs and reuse prior sections. Import the latest saved HTML snapshot with scripts/update.py; do not replace personal notes with a fresh build. Keep course-specific progress/coverage and new revision filenames. Stop for conflicting edits or revised processed files and reconcile explicitly.
- Build with scripts/build.py and validate with scripts/validate.py. After template/runtime changes run unit and browser tests, including export/reopen and mobile layouts.
- Do not launch a Scientific Correctness Reviewer subagent for Study Suite HTML creation, authoring, remakes or updates. The primary author checks factual accuracy against the supplied sources. Only an explicit user request for a scientific-review agent on that task overrides this exclusion; ordinary new-course delivery is not a scientific-review milestone.
- The public repository contains reusable source, tests, docs and the intentional synthetic demo. Keep logs, test downloads, screenshots, work/, credentials and real course materials out.

- Visual acceptance includes full-viewport balance: reject large empty lanes under unequal cards and orphan figures. Group related diagrams alongside explanation stacks when appropriate. Measured card packing must react to resize/disclosure/editing, stay within topic boundaries, and discard viewport-specific measurements on export. Passing overflow checks does not establish a good composition.
