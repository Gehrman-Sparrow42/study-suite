# Content schema · version 3

Use UTF-8 JSON. All text is English. Text fields are escaped prose with restricted emphasis and list syntax, not arbitrary HTML or general Markdown. The builder escapes HTML. Within summaries, bodies, steps and table cells, explicit `\(LaTeX\)` denotes editable inline mathematics. In JSON, escape each backslash: `"The quantity is \\(q=12\\)."`. For display math, use a `formula` block with raw `latex` and no delimiters. Unicode symbols are also useful in prose.

## Course object

```json
{
  "schema_version": 3,
  "language": "en",
  "synthetic": false,
  "title": "Course title",
  "subtitle": "Brief scope and reading orientation.",
  "included_section_ids": ["foundations"],
  "sections": [
    {
      "id": "foundations",
      "title": "Foundations",
      "intro": "A short bridge into this section.",
      "blocks": [
        {
          "type": "concept",
          "category": "definition",
          "title": "The core idea",
          "summary": "The essential teaching statement remains visible in Review.",
          "body": "Explain how and why. Separate paragraphs with two newline characters.",
          "source": "Lecture 1, slides 4–6."
        }
      ]
    }
  ]
}
```

`schema_version`, `language`, `synthetic`, `title`, `subtitle`, `included_section_ids` and a nonempty `sections` array are required. `synthetic` must be explicitly false for real course output. The builder rejects obvious demo/placeholder markers in production data; the author still verifies the whole document.

Section IDs must be unique lowercase slugs matching `[a-z][a-z0-9-]*`. The generated anchor is `section-<id>`, preventing collisions with reader controls. `included_section_ids` must contain each section ID exactly once: reconcile it with the saved topic coverage map. Every section needs a nonempty `blocks` list. `intro` is optional.

## Common block fields

- `type`: one of the types below. Unknown types are rejected, including quizzes and flashcards.
- `title`: required, editable heading.
- `summary`: required for every type except figure; visible in both reading modes. Keep essential assumptions here or in persistent steps. For `worked`, explicitly state the problem and required output, not merely the answer; supply essential givens here or in a clearly associated persistent component before the first calculation.
- `body`: optional expanded explanation. Two newlines separate paragraphs. Hidden in Review, temporarily visible when searching.
- `category`: `definition`, `process`, `formula`, or `warning`. Defaults to process for process blocks, formula for formula/worked blocks, definition otherwise.
- `source`: optional short provenance text, displayed in collapsed Source note details when source labels are enabled.
- `compact`: optional boolean; pairs short concept/prose blocks on wide screens. Other types remain full width.
- `learn_only`: optional boolean, default false. Hides the entire block in Review and labels it Further explanation. Use it for expanded bullet explanations that accompany a core block. Matching search results can reveal it temporarily, as with ordinary explanatory bodies. Keep essential formulas, symbol definitions, assumptions and short takeaways in persistent blocks.

## Weekly metadata and snapshots

Existing schema version 3 remains compatible. For incremental courses add `course_id` (a stable lowercase slug), a stable `id` on every block, and positive integer `week` on each section. Section/block IDs use the same slug syntax. Block IDs are unique within their section. Missing course/block IDs are generated by the builder; explicit persistent IDs are preferred for weekly authoring. Numbered weeks sort numerically; unnumbered sections appear first and within-week order is stable.

Course `sources` is a list of `{ "path": "week-06.pdf", "sha256": "64 lowercase hexadecimal characters", "week": 6 }`. Paths are relative to the chosen input material directory, use forward slashes and cannot traverse outside it. Section `source_files` lists the source paths used by that section. The incremental updater verifies that added sections refer to newly processed sources of the same week. Existing `source` prose labels on blocks remain useful for slide/page provenance.

A weekly delta contains `schema_version: 3`, matching `course_id`, nonempty `sources` and `sections`; the sections use the normal block schema. It does not repeat old sections. See `demo/week_06.delta.json` and WEEKLY_UPDATES.md.

Built HTML includes a versioned JSON baseline and changed-field snapshot in `script#suite-state`. Save Progress and Auto-save refresh the changed fields from the editable DOM. This metadata lets the updater reconcile saved notes by stable IDs; it is not a second summarizer or a requirement to hand-edit HTML metadata. Preserve it when saving. Plain-text paragraph boundaries and raw math are retained; arbitrary browser styling is not imported to JSON.

## Block types

| Type | Extra fields | Behavior |
| --- | --- | --- |
| `concept` | none | Core concept or limitation; optional compact layout |
| `prose` | none | Explanatory connection; optional compact layout |
| `process` | `steps`: nonempty array of strings | Persistent numbered mechanism/sequence |
| `formula` | `latex`: raw LaTeX string | Rendered display formula, source editor, explanatory body |
| `comparison` | `headers`: strings; `rows`: arrays of strings | Table with matching row widths and editable cells |
| `worked` | `steps`: nonempty array of strings | Problem/required result in summary, supplied data before calculations, then fully explained solution; no answer interaction |
| `figure` | asset, origin, alt, caption, credit | Embedded image and zoomable lightbox |
| `review` | `steps`: nonempty array of strings | Section takeaway with persistent bullet points |
| `details` | optional body | Supplementary explanation, open in Learn by default |

Formula example:

```json
{"type":"formula", "title":"Average rate", "summary":"Change in amount per unit time.", "latex":"\\bar{r}=\\frac{\\Delta q}{\\Delta t}", "body":"Define the quantity and interval, and state the conditions."}
```

Figure example:

```json
{"type":"figure", "title":"Source diagram", "asset":"assets/lecture-1-slide-4.png", "origin":"slide", "alt":"Describe the important spatial or causal relationship.", "caption":"Explain what to notice.", "credit":"Lecture 1, slide 4; supplied course material."}
```

`asset` is relative to the JSON file's directory and must resolve inside that directory. Supported suffixes: png, jpg/jpeg, webp, svg. SVG must be static and self-contained (no scripts, external references, stylesheets, foreignObject, image or use elements); use simple shapes/text or rasterize complex artwork. Asset size limit: 8 MiB per image. Missing selected assets fail the build. A figure excluded by visual policy is not read.

`origin` is `slide`, `custom` or `web`. Web figures additionally require an HTTPS `source_url` and a `license` string. The author must verify rights; a metadata string does not establish permission. All assets are embedded locally; no hotlinks.

## Authoring constraints

The schema is deliberately narrow. It does not accept arbitrary executable HTML, custom widget code, question banks or review quizzes. For additional teaching patterns, first express the material through the existing components. Extend the reusable renderer only when the learning benefit justifies new maintenance and tests.

Browser edits modify the exported HTML, not this JSON. To incorporate those edits into a future rebuild, explicitly reconcile them into the authored source; never silently overwrite an edited edition.


## Restricted reading formatting

Use `**term or short lead-in**` for selective bold emphasis in summaries, bodies, steps and table cells. General HTML and Markdown are not accepted. Do not nest bold around inline mathematics or use unmatched markers intentionally.

In `body`, separate prose paragraphs and bullet groups with a blank line. Each simple bullet begins with `- ` on its own line; a group consists entirely of those lines. The builder produces a semantic ul/li list inside the same editable explanation host, not another card. Nested lists, ordered Markdown lists and multiline bullet syntax are not supported; use existing process/worked steps for numbered mechanisms.

Example body: `Useful products:\n\n- **Lipids:** a possible fuel feedstock.\n- **Carbohydrates:** another possible conversion feedstock.\n\nSuitability depends on the organism and process.` In JSON these newline escapes become real line breaks. The full body still hides in Review. Essential limitations must remain in persistent content.

Save/export, recovery and weekly snapshots preserve these authored markers. When updating an older HTML to use this formatting, also update its reader runtime through a deliberate rebuild from reconciled source; changing DOM alone does not give old recovery code the new syntax.

### Visual process chains

A `process` block can set `"presentation": "flow"` to render its existing ordered `steps` as an arrow-connected vertical chain. Omit this field (or use `"list"`) for a normal numbered sequence. Other block types reject this field. Example: `{"type":"process","title":"Conversion chain","summary":"An input becomes a useful output.","presentation":"flow","steps":["**Input:** collect the feed.","**Conversion:** transform the feed.","**Output:** recover the product."]}`. These are synthetic authoring examples, not course facts. Every step retains its editable pointer and is visible in Review unless the whole block is explicitly learn-only. Body explanations use native disclosures, open by default; no new body field or schema version is required.

### Companion figure placement

A figure may set `"placement": "alongside"`. It groups the preceding consecutive ordinary cards in the section (since the last comparison/review boundary) into a text stack beside the figure. Use only for a meaningful topic relationship. At narrow widths, text then figure follow the same DOM order. The field is rejected on other block types or with other values. It does not alter editable fields or source content. Without preceding cards the figure uses ordinary layout.

### Persistent structured summaries and compact comparisons

A summary can contain blank-line-separated paragraphs or simple bullet groups using the same safe formatting as body text. They stay inside one editable host and remain visible in Review; this is useful for separate Problem, Given/Assume, Find and Boundary paragraphs before a worked solution. Retain essential inputs here rather than placing them in foldable body text.

A comparison can set `"compact": true` to share a responsive card group with related explanations or process flows. Use it for a small, readable table (often two columns). Omit it for a wide comparison that should separate topic groups. This is an authoring decision based on the table's content, not a blanket rule to shrink all tables.
